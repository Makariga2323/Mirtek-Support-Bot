# Правида работы с репозиторием

##Ветки

| Ветка | Назначение | Как попажает код |
|---|---|---|
| 'main' | Релиз. Всегда рабочая. | Только через PR из 'dev' |
| 'dev' | Разработка. Сюда собирается всё готовое. | Только через PR из рабочих веток |
| 'feature/<кратко>' | Новая функциональность | Создаётся от 'dev', PR в 'dev' |
| 'fix/<кратко>' | Исправление ошибки | Создаётся от 'dev', PR в 'dev' |
| 'docs/<кратко>'| Документация | Создаётся от 'dev', PR в 'dev' |

Прямые 'git push' в 'main' и 'dev' запрещены. Всё идет через Pull Request.

Примеры имён: 'feature/store-hours', 'fix/price-rounding', 'docs/readme-update'.

## Рабочий процесс

1. 'git checkout dev' and 'git pull' : встать на 'dev' и обновиться.
2. 'git checkout -b feature/название': создать ветку под задачу.
3. Писать код, делать коммиты.
4. 'git push - u origin feature/название': отправить сетку на GitHub.
5. Открыть Pull Request **в 'dev'**.
6. Дождаться ревью и одобрения, внести правки, если просят.
7. Влить PR, ветку удалить.
8. Когда в 'dev' накопится стабильная версия, открыть PR 'dev' -> 'main'.

## Коммиты

Формат: 'тип: описание', например 'feat: добавить ответ о режиме работы'.
Типы: 'feat' (новое), 'fix' (исправление), 'docs' (документация), chore (служебное).

## Pull Request

1. Один PR, одна задача.
2. PR открывается **в 'dev'**. В 'main' только из 'dev'.
3. Заголовок в том же формате, что и коммит.
4. Заполните шаблон: что сделано, как проверить.
5. Нужно минимум **1 одобрение** другого участника.
6. Автор не одобряет и не вливает свой PR сам.
7. Если PR отстал от 'dev' снчала подтяните свежий 'dev': 'git merge origin/dev'.
8. В PR не должно быт паролей, '.env' и посторонних файлов.
9. После вливания ветку удаляем.

## Ревью

- Откройте вкладку **Files changed**, прочитайте изменения.
- Комментируйте конкретные строки и предлагайте решение.
- Итог: **Approve** (можно вливать), **Request changes** (нужны правки).
- Автор отвечает на комментарии и пушит правки в туже ветку.
