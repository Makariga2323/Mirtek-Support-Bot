# Основа приложения: хранение, повторы, восстановление

Документ описывает решения TASK-09. Код: `backend/main.py`, `backend/service/`.

## Слои

API (`main.py`) → `MessageService` → ядро (`Core`) и `Storage` (SQLite).
В режиме `CORE_MODE=stub` ядро это старая `answer_for` в обёртке `StubCore`.

## Состояния сообщения

`processing` → `answered` | `too_complex` | `failed` (причины: `timeout`, `core_error`, `interrupted`).
Клиент внутренний `failed` не видит: он отдаётся как `too_complex` с действием `escalate`.

## Повторы

Ключ: пара `session_id` + `client_message_id`, уникальность проверяет база.
- Повтор готового сообщения возвращает сохранённый результат, ядро не запускается, `latency_ms` тот же.
- Повтор во время обработки ждёт в пределах бюджета времени запроса.
- Повтор после `failed` запускает ядро заново (`attempts` растёт).
- Без `client_message_id` каждое сообщение новое.

## Ошибки и время

Бюджет одного запроса: `REQUEST_BUDGET_S` (по умолчанию 5 с). Таймаут даёт `failed/timeout`, падение ядра `failed/core_error`.
Опоздавший ответ ядра никуда не записывается: статус пишет только сервис.
Сбой хранилища даёт 503 без подробностей, подробности только в журнале.

## Заявки оператору

Один `idempotency_key` соответствует одной заявке. Тот же ключ для другого сообщения или из другой сессии даёт 409.

## Хранение и очистка (решение для MVP)

Данные живут не дольше сессии: выход из чата или истечение `SESSION_TTL_S` удаляет сессию, а вместе с ней сообщения и заявки (каскад в базе).
Просроченные сессии удаляются при старте сервера и при каждом входе.
Если заявки должны переживать сессию, их надо хранить отдельно и не удалять каскадом (решение на будущее).

## Восстановление после перезапуска

При старте все сообщения в `processing` помечаются `failed/interrupted`: сервер один, значит, они оборвались вместе с прошлым процессом.
При каждом входе дополнительно помечаются сообщения, которые висят в `processing` дольше `STALE_PROCESSING_S` (по умолчанию 60 с).
Клиент повторяет запрос с тем же `client_message_id` и получает ответ.

## Ограничения MVP

- Один процесс сервера. При нескольких процессах стартовое восстановление нужно заменить проверкой по возрасту.
- Зависший вызов ядра занимает поток из пула (4 потока); реальное ядро должно уважать `Deadline` и иметь свои таймауты.
- Идентификаторы `msg-N` и `ticket-N` последовательные; доступ защищён проверкой сессии.
